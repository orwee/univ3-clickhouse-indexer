1.24 million trades from a public ledger, loaded into ClickHouse, modelled with dbt and checked against the ledger and an independent source. On top: an agent that answers questions about the data by writing SQL, and an evaluation that measures how often it is right, when it refuses, and what each answer costs.

Background

In plain words

The ledger is Ethereum, and the trades are on Uniswap v3, an exchange that runs on it. Three words are enough to follow the rest.

Token
A currency that lives on the ledger. USDC is a dollar. WETH is ether in a form a contract can hold.
Pool
A contract that holds two tokens and trades one for the other with anyone, for a fixed fee. The project follows four pools.
Swap
One trade against a pool: some of one token in, some of the other out. Every swap leaves a public record, and those records are the rows here.

Findings

Including the ones that did not work

Each change was written down with its metric and its rule before it ran, and is reported whatever it showed.

Improved

One paragraph fixed a class of failures

Most errors on the harder set were the same: refusing a day on which a pool had no trades, where the answer is zero. The fix was written from the design questions only and measured on held-out ones. It is not the default yet: the version meant for daily data fell one refusal short of its rule.

My bug

The first alarm was in the measurement

About one answer in six looked as if it was not taken from a query result. Reading them showed the check, not the agent, was wrong. Fixed as a measurement bug, not claimed as an improvement.

No difference

Changes that did not move the number

A prompt change for refusals made no difference: 17 of 21 refused before and after. Caching and the daily version of the fix each missed a rule by one case. Lesson: set those rules from the variation between identical runs.

Incomplete

A cheaper gateway was not a drop-in

The same model through a discount gateway ended in an error on 8 of 53 questions and was nearly three times slower (15.3 s against 5.6 s): it cannot take back the model's signed reasoning. No saving claimed.

Known limits

What is not done yet

  • No person has labelled anything yet: the judge and the documentation search are scored against labels written by a model.
  • Every figure is for one model, Claude Haiku. One run of a larger model on the design questions is not a comparison, and no other provider has completed a run.
  • The agent has only run on a committed copy of the data, never on the live database. Refusals are its weak spot: a few questions the data cannot answer still get a number.
  • The read-only database user is in force in CI and in the demo, but opt-in on the real server and not turned on there.
  • The Airflow DAG is opt-in and has not added a day: the data still ends on 2026-09-25.
  • Differences with the external source can be located but not settled: it publishes no methodology.
